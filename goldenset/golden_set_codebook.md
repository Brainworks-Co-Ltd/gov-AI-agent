# 골든셋 라벨링 코드북

날짜: 2026-08-26

## 0. 이 문서를 왜 쓰는가

`tests/golden_set`을 5건(공고문001~005) → `공고문 라벨링/`에 이미 있는 006번
이후 문서로 확장하기 전에, 필드별 라벨링 규칙을 명문화한다. 지금까지는
라벨러 한 명("나")이 001~005를 라벨링하면서 암묵적으로 적용한 기준이 있는데,
이 기준이 문서에 남아있지 않으면 006번 이후를 라벨링할 때(같은 사람이라도
시간이 지나면) 기준이 흔들릴 수 있다. 특히 `docs/structuring_prompt_improvement.md`가
이미 기록한 실패 패턴(요약해서 감점, 평가항목/평가기준 혼동, "빠짐없이
나열" 지시의 부작용)은 AI 추출뿐 아니라 사람 라벨링에도 똑같이 함정이 될 수
있어서 미리 명시해둔다.

**골든셋의 두 가지 쓰임새**: (1) 원래 목적인 5단계 구조화 엔진 정확도 검증
(`scripts/validate_golden_set.py`), (2) 이번에 새로 정식화하는 것 — 신청자격
진단 엔진(`app/pipeline/eligibility/engine.py`)의 조건 분류(A-서류형/A-코드형/
B-주관형)가 맞는지 검증하는 데도 재사용 가능하다. 3절 "판단유형" 참고.

## 1. 라벨링 산출물 형식

- 소스: `공고문 라벨링/데이터_전처리_v９.xlsx`(파일명의 숫자 9는 전각문자
  `９`다 — 반각 `9`로 찾으면 안 나온다), `Sheet1`, long format(문서 하나당
  필드 개수만큼 행이 생김). 이전 버전(v8 이하)은 `공고문 라벨링/old/`에
  보관돼 있으니 참고용으로만 쓴다.
- 컬럼: `문서ID` / `필드명` / `정답값` / `근거_페이지` / `근거_원문발췌` /
  `판단유형` / `라벨러이름` / `비고`.
- `문서ID`: `공고문NNN` (3자리). 번호는 `공고문 라벨링/파일명_매핑.csv`의
  기존 번호를 그대로 쓴다 — 새로 매기지 않는다.
- 이 xlsx를 `python -m scripts.build_golden_set_from_xlsx`로 돌리면
  `tests/golden_set/cases/<문서ID>/answer.json`이 자동 생성된다. 새 문서를
  추가하면 스크립트 상단의 `SOURCE_EXTENSIONS`, `GOLDEN_SET_ROUTE_LABELS`
  딕셔너리에도 등록해야 한다(4절 참고).

## 2. 필드별 라벨링 규칙

공통 원칙 — **원문을 요약하지 않는다.** `docs/structuring_prompt_improvement.md`
11절에서 정답과 AI 답을 직접 비교한 결과, 감점의 압도적 1위 원인은 "AI가
맞았는데 짧게 요약해서"였다: 정답은 법조항 번호·정확한 금액·①②③ 세부조건까지
그대로 옮겨 적혀 있는데 AI는 핵심만 간추린 것이 원인이었다. 정답 라벨 자체가
간추려져 있으면 이 비교가 애초에 성립하지 않는다 — 사람이 라벨링할 때도
공고문 원문 표현을 최대한 그대로 옮긴다.

### 사업명 (`business_name`)

공고문 표지/제목에 나온 정식 사업명 그대로. 부제가 있으면 포함.

### 신청기간 (`application_period`)

접수 시작일~마감일을 원문 표기 그대로("2026.08.20 ~ 09.09"처럼 종료일의
연도가 생략돼 있으면 생략된 그대로 옮기고, 사람이 임의로 채워 넣지 않는다).
마감 시각(예: "16:00까지")이 명시돼 있으면 포함한다.

### 지원대상 (`eligibility`)

신청 가능한 대상 요건(적극적 조건). 여러 조건이 AND로 묶여 있으면
("1번 조건: ... && 2번 조건: ...") 조건 사이의 관계가 드러나게 하나의
문자열 안에 구분해서 담는다 — 신청제외대상과 달리 리스트로 쪼개지 않는다.
조건 개수가 대체로 적고 AND로 묶여야 의미가 통하는 경우가 많아서, 개별
리스트로 쪼개면 오히려 조건 간 관계 정보가 사라지기 때문이다.

**OR로 묶인 경우** ("다음 중 하나에 해당하는 자")는 반대로 **리스트로
쪼갠다** — 신청제외대상_항목과 같은 방식(항목별로 행을 나누고 판단유형도
항목마다 매김). 신청제외대상_항목이 이미 "리스트의 각 항목 = 독립적
충분조건"이라는 의미로 쓰이고 있어서(하나라도 해당하면 제외), OR 조건도
같은 의미 구조이므로 리스트로 쪼개도 관계 정보가 사라지지 않는다. 단,
AND와 OR이 섞인 조건("A 그리고 (B 또는 C)")은 리스트로 평평하게 쪼개면
중첩 구조가 깨지므로, 이 경우는 AND와 마찬가지로 하나의 문자열 안에
관계를 텍스트로 남긴다.

**판단유형을 함께 매긴다** (3절 참고). 지원대상은 조건이 여러 개 섞인 경우가
많으므로 해당하는 코드를 전부 쉼표로 나열한다(예: `①,②`).

### 신청제외대상_항목 (`exclusions`, 리스트형)

신청이 제외되는 대상 항목들.

- 공고문에 번호(①②③...)가 매겨져 있으면 그 번호를 그대로 유지한 채 항목별로
  엑셀 행을 나눈다. `필드명` 칸에 `신청제외대상-① <항목 원문>` 형식으로 적는다
  (스크립트의 `LIST_FIELD_PREFIXES`가 "신청제외대상"으로 시작하는 필드명을
  모두 `신청제외대상_항목` 리스트 하나로 합친다).
- 번호가 없는 산문형 조항은 사람이 의미 단위로 쪼개되, 원문 문구를 최대한
  보존한다.
- **항목마다 판단유형을 반드시 매긴다** — 이번에 정식 규칙으로 못박는 부분.

### 지원금액 (`support_amount`)

지원 금액 또는 지원 내용. 상한액, 조건부 단계별 금액(예: "사업화자금 최대
1억원, 후속 연계지원 최대 2년 6억원")까지 원문 그대로.

### 기업 부담금 (`company_contribution`)

기업이 부담해야 하는 금액. 명시가 없다고 빈 문자열로 두지 않는다 — 공고문에
"자기부담금 없음"류 문구가 실제로 있는지 확인한 뒤 없으면 `없음`으로 채운다
(`schema.py`가 이 필드를 "없으면 '없음'"으로 정의해뒀고, `validator.py`가
필수 필드로 검사하므로 빈 문자열이면 검증 실패로 잡힌다).

### 제출 서류 (`submission_documents`, 리스트형)

제출해야 하는 서류 항목들. 신청제외대상_항목과 같은 번호분리 방식 —
`필드명` 칸에 `제출 서류-① <서류명>` 형식. 필수/해당시/증빙 같은 구분은
태깅하지 않는다(공고문마다 표현이 제각각이라 `schema.py` 주석에도 이미
명시된 기존 방침).

### 평가 (`evaluation_items`, 구조화 리스트) / 평가 비고 (`evaluation_notes`)

**2026-08-26 스키마 변경**: 예전엔 "평가 항목"(절차·카테고리명)과 "평가 기준"
(배점·세부내용)을 별도 문자열 두 개로 라벨링했는데, `docs/
structuring_prompt_improvement.md` 3절대로 AI가 표의 세부평가/배점 열을 어느
쪽에 넣을지 실험마다 계속 헷갈렸다(한쪽을 고치면 다른 쪽이 나빠지는
트레이드오프가 반복 확인됨). 그래서 두 필드를 항목별 구조화 리스트
`평가`(항목명/배점/세부내용) + 잔여정보 `평가 비고` 하나로 합쳤다 — 표의 행
하나가 리스트의 항목 하나로 자연스럽게 대응되게 해서, "어느 문자열에
넣을지" 판단할 경계 자체를 없앴다.

**엑셀 작성법**: 항목 하나당 최대 3개 행을 쓴다 — `필드명` 칸에
`평가-①-항목명`, `평가-①-배점`, `평가-①-세부내용` (번호는 ①②③... 순서대로,
읽기 쉬우라고 번호 뒤에 설명을 덧붙여도 됨, 예: `평가-① 기업 비전 및
사업성-항목명`). 배점·세부내용이 없는 항목(절차형 단계 등)은 그 행을 아예
안 쓰면 된다(자동으로 `null` 처리됨). `scripts/build_golden_set_from_
xlsx.py`의 `_EVALUATION_ROW_RE`가 이 패턴을 인식해서 번호별로 묶는다.

- 공고문에 평가표(세부평가/평가내용/배점 열이 있는 표)가 있으면 **표의 행
  하나 = 항목 하나**로 그대로 옮긴다. 항목명 열 → `항목명`, 배점 열 →
  `배점`, 나머지 설명 열 → `세부내용`.
- 표가 없고 "서류심사 → 발표평가"처럼 절차·단계 나열형이면, **단계 하나 =
  항목 하나**로 만들고 `항목명`에 단계 이름을, 그 단계에 딸린 설명이 있으면
  `세부내용`에 옮긴다. `배점`은 비워둔다.
- 컷오프 점수("취득점수 60점 미만 시 제외"), 평가 방법·구성 인원, "배점표는
  공고문에 미기재" 같이 **특정 항목 하나에 안 붙는 잔여 정보**는 `평가 비고`
  (`필드명` 칸에 그대로 `평가 비고`)에 적는다. 항목 안에 억지로 끼워넣지
  않는다.
- **한 문서 안에 표형/절차형이 섞여 있는 경우**(예: 1차 서류심사는 배점
  없는 통과·탈락, 2차 발표평가만 세부 배점표가 있음)도 배점 유무와 무관하게
  전부 `평가` 리스트의 항목으로 넣는다 — 배점이 없다고 절차형 단계를
  `평가 비고`로 빼지 않는다. `배점`이 없으면 그 행만 비워두면 된다(자동
  `null` 처리).

### 유의 사항 (`notes`)

`docs/structuring_prompt_improvement.md` 12절(실험 E): "빠짐없이 나열하라"는
지시가 AI로 하여금 인접한 무관 섹션(신청절차 안내, 심지어 평가 기준 내용)을
끌어오게 만든 실패 사례가 있었다. 사람이 라벨링할 때도:

- 공고문의 "유의사항"(또는 동등한) 섹션 제목 아래 있는 "위반 시 불이익/제재"
  류 문구만 포함한다.
- 신청 절차 안내나 평가 관련 내용을 유의사항으로 끌어오지 않는다 — 각 필드는
  공고문의 해당 섹션 제목을 기준으로 귀속시킨다.

### 주관기관 — 이번에도 라벨링하지 않음

`schema.py`에 필드는 있지만("추출은 시도하되") 골든셋 정답이 없어서 검증
대상에서 제외돼 있다(`schema.py` 모듈 docstring에 명시). 006번 이후 문서도
동일하게 라벨링하지 않는다 — 필요해지면 이 코드북과 스크립트를 함께 고친다.

## 3. 판단유형 코드 — 이번에 정식화

xlsx 헤더에 `판단유형: ①규칙 / ②서류검증 / ③종합판단 / ④우선순위 /
⑤결격조회`라는 약어 정의만 있고 상세 기준은 없었다. 001~005를 실제로 라벨링한
값(52건)을 근거로 각 코드의 의미를 아래처럼 못박는다. `지원대상`과
`신청제외대상_항목`의 각 조건에 매긴다(지원대상처럼 복합조건이면 여러 개를
쉼표로).

| 코드 | 의미 | 예시(001~005 실라벨) |
|---|---|---|
| ① 규칙 | 업종코드(KSIC)·수치·기간처럼 기계적으로 대조 가능한 규칙 | "창업 제외 업종 영위자", "신청일 기준 휴·폐업 중인 자", "업력 7년 이내" |
| ② 서류검증 | 공식 발급 서류의 보유 여부로 확정 가능 | "국세·지방세 체납 중인 자"(완납증명서), "자사명의가 아닌 대리참가"(사업자등록증) |
| ③ 종합판단 | 서류·코드로 판정 불가, 심사위원/담당자 정성판단 필요 | "사회적 물의·과거 사업 심각한 차질", "상용화된 AI 솔루션 미보유 기업" |
| ④ 우선순위 | 자격의 O/X가 아니라 동순위 후보 중 우선 선정 기준 | (011 유형) "신규채용 근로자 유무에 따른 1~4순위" |
| ⑤ 결격조회 | 정부·공공 시스템의 명단/이력을 조회해야 확인 가능 — 신청자가 스스로 보유한 서류가 아님 | "체불사업주 명단 포함자", "중기부 창업지원사업 참여제한 제재 중인 자", "보조금관리법 수행대상 배제자" |

**②서류검증 vs ⑤결격조회 경계**: "결격사유 없음 확인서를 제출하되, 최종
확정은 중기부 시스템 조회로 이뤄진다"처럼 신청자 제출서류와 정부 조회가
둘 다 관련된 조건은 **신청자 행위 기준으로 ②**를 매긴다 — 신청자가 뭘
제출/증빙하는지가 기준이고, 최종 판정을 누가 하는지는 무시한다. ⑤는
신청자가 애초에 보유·제출할 서류 자체가 없고(명단·이력 조회로만 확인
가능) 오직 담당기관 조회로만 알 수 있는 경우로 좁혀서 쓴다.

**왜 이 코드가 중요한가**: `classify_condition()`이 반환하는 `condition_type`
(A-서류형/A-코드형/B-주관형)과 사실상 대응한다 — ①규칙→A-코드형, ②서류검증
→A-서류형, ③④⑤→B-주관형(엔진이 서류·코드로 확정 못 해 사람에게 넘기는
것들의 세부 사유). 지금은 이 둘을 자동으로 비교하는 채점 스크립트가 없지만,
판단유형을 일관되게 쌓아두면 나중에 "엔진이 낸 분류가 사람이 매긴 판단유형과
맞는가"를 자동 채점하는 스크립트를 훨씬 쉽게 만들 수 있다.

주의: ④·⑤는 지금 신청자격 진단 엔진이 구조적으로 다루지 못하는 영역이라는
게 매핑테이블 확장 작업(실제 공고문 리뷰)에서도 이미 확인됐다 — 그래도
라벨은 정직하게 매겨서 "엔진이 여기서는 확인필요로 폴백하는 게 맞다"는 것
자체를 검증할 수 있게 한다.

## 4. 신규 문서 추가 절차 (006번 이후)

1. `공고문 라벨링/파일명_매핑.csv`에서 원본파일명 ↔ `공고문NNN` 대응을
   확인한다. **주의**: 2026-08-26 이후 번호를 다시 매기면서 이 CSV가
   실제 `공고문 라벨링/` 폴더 내용과 어긋난 적이 있었다(확장자 불일치 등).
   새 문서를 추가하기 전에 CSV의 해당 행이 실제 폴더 파일과 일치하는지
   먼저 눈으로 확인한다.
2. 신청서/참가신청서 서식(공고문 자체가 아닌 것)은 골든셋 대상에서
   제외한다 — 2026-08-26 당시엔 `006`, `010`이 여기 해당했지만, 번호를
   다시 매기면서 지금은 참가신청서 서식이 남아있지 않다(006·010도 이제
   정식 공고문). **고정된 번호를 믿지 말고, 매번 파일을 열어 신청서
   서식인지 공고문인지 직접 확인한다.**
3. hwp/hwpx 문서는 LibreOffice로 PDF 변환 후 읽는다(`app/pipeline/normalize/
   hwp_converter.py`의 변환 결과 재사용 가능). PDF는 네이티브 텍스트가
   있으면 그대로 읽고, 스캔 이미지면 원본을 열어 직접 읽는다.
4. 위 필드별 규칙에 따라 `데이터_전처리_v8.xlsx`에 long-format 행을
   추가한다(새 시트를 만들지 않고 같은 시트에 이어 붙인다).
5. `scripts/build_golden_set_from_xlsx.py`의 `SOURCE_EXTENSIONS`,
   `GOLDEN_SET_ROUTE_LABELS`에 새 문서ID를 등록한다(표/스캔 유무는 PDF를
   직접 열어 육안으로 확인 — 자동으로 채울 수 없음).
6. `python -m scripts.build_golden_set_from_xlsx` 실행 →
   `tests/golden_set/cases/공고문NNN/` 생성 확인.
7. `pytest -m golden -v`로 회귀 확인 (실제 OCR·LLM API를 호출해 과금 발생하므로
   수동 실행 — `pytest.ini` 참고).
