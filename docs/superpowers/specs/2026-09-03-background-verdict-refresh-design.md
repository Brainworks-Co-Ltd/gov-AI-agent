# Design: 데모용 판정 결과 사전 갱신

Status: APPROVED
Approved-by: 사용자의 “그렇게 구현해줘” 요청
Scope: 단일 회사 프로필을 사용하는 데모 서버

## 목표

공고함을 열 때 LLM 판정을 시작하지 않고 SQLite에 저장된 판정 결과만 즉시 보여 준다.
무거운 수집·중복 통합·판정은 웹 버튼이나 외부 예약 작업이 같은 갱신 파이프라인을
호출해 백그라운드에서 수행한다.

## 현재 상태

- `data/app.db`에 공고·중복 묶음·판정 결과가 이미 저장된다.
- 목록을 열면 미판정 공고 12건을 자동 판정한다.
- `목록 전체 판정`은 브라우저가 4건씩 반복 요청하므로 브라우저가 작업을 붙들고 있다.
- 판정 캐시는 회사 프로필 해시만 검사한다. 공고문이나 판정 로직이 바뀌어도 예전 결과가
  유효한 것처럼 보일 수 있다.
- SQLite는 기본 DELETE 저널 모드다.

## 설계

### 판정 캐시 유효성

판정 결과마다 `input_hash`를 저장한다. 해시는 다음 입력으로 만든다.

1. 회사 프로필 해시
2. 대표 공고와 같은 중복 묶음의 공고 본문
3. 판정 캐시 버전

세 값 중 하나가 달라지면 해당 공고만 미판정으로 취급한다. 날짜에 따라 달라지는 D-day는
캐시를 무효화하지 않고, 캐시를 읽을 때 현재 날짜로 다시 계산한다.

### 갱신 파이프라인

`tools.refresh`가 다음 두 실행 경로를 제공한다.

- `python -m tools.refresh`: 저장된 공고 중 신규·변경·구버전 공고만 판정
- `python -m tools.refresh --collect`: 공식 API 수집과 중복 통합 후 필요한 공고만 판정

웹의 `목록 전체 판정`과 `공고 새로 수집`도 같은 파이프라인을 백그라운드 스레드에서
실행한다. 동시에 두 작업을 시작하지 못하도록 프로세스 안에서 잠근다. 서버가 중간에
재시작돼도 이미 저장된 건은 다시 쓰지 않고 남은 건부터 이어서 계산한다.

### 웹 동작

- 최초 목록 조회에서는 자동 판정을 실행하지 않는다.
- 갱신 버튼을 누르면 서버는 즉시 작업 시작 상태를 반환한다.
- 브라우저는 상태 API만 주기적으로 조회해 진행률을 표시한다.
- 작업이 끝나면 목록을 다시 읽어 최신 집계와 배지를 표시한다.

### SQLite 동시성

모든 연결에 WAL과 `busy_timeout`을 적용한다. 백그라운드 작업이 결과를 쓰는 동안 일반
웹 요청은 마지막으로 커밋된 결과를 계속 읽는다. SQLite 파일은 같은 호스트의 로컬
디스크에 둔다.

## 범위 밖

- 사용자 계정·회사별 프로필 분리
- 외부 PostgreSQL 도입
- 예약 시각을 애플리케이션 설정으로 관리
- 여러 서버 인스턴스에서 동시에 같은 SQLite 파일 사용

예약 실행은 운영체제 작업 스케줄러나 배포 플랫폼의 예약 작업에서 CLI 명령을 호출한다.

## 완료 조건

- 목록을 열어도 LLM 판정 요청이 자동 발생하지 않는다.
- 버튼 요청은 무거운 작업 완료를 기다리지 않고 즉시 반환한다.
- 신규·변경 공고와 프로필·판정 버전 변경만 재판정한다.
- 기존 DB가 자동 마이그레이션되고 기존 판정은 안전하게 구버전으로 취급된다.
- 백그라운드 쓰기 중에도 목록 조회가 가능하다.
- 기존 자격 판정 테스트와 신규 캐시·갱신 테스트가 통과한다.
