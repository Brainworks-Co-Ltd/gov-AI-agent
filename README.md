# 정부지원사업 공고 자동 분석 · 신청서 초안 생성

「2026 전남광주 청년(Youth) AI 솔버톤」 **트랙 B-08** 과제 구현.

기업마당·K-Startup에 흩어진 정부지원사업 공고를 오픈API로 모아 **중복을 통합**하고,
회사 프로필과 대조해 요건별 **가능 / 불가 / 확인필요**를 판정하며, **신청서 초안 생성과
제출 전 점검**까지 해 주는 웹 도구입니다.

> **해결하려는 문제** — 전자부품 제조업 / 10인 미만 / 스마트시스템 미도입 기업의 경영기획
> 담당자 1인이 매일 여러 기관을 확인해 지원금액·자격·마감일을 엑셀에 수기로 정리하고,
> 공고별 양식에 맞춰 신청서를 반복 작성합니다. **건당 2~4시간**이 들고, 서류 누락·일정
> 착오·문서 간 수치 불일치 위험이 담당자 한 사람에게 몰려 있습니다.

## 빠르게 실행하기

Python 3.10 이상만 있으면 됩니다. **설치할 패키지가 없습니다**(전부 표준 라이브러리).

```bash
python -m tools.refresh --collect  # 수집 + 중복 통합 + 필요한 공고만 사전 판정
python serve.py                    # http://localhost:8000
```

인증키가 아직 없다면 마지막 수집분 캐시로 띄울 수 있습니다:

```bash
python -m tools.refresh --collect --offline
```

웹은 SQLite에 저장된 판정 결과만 읽으므로 공고함을 여는 순간에는 LLM을 호출하지
않습니다. `공고 새로 수집`과 `판정 결과 갱신` 버튼도 같은 작업을 백그라운드에서
실행하므로, 갱신 중에도 저장된 결과를 계속 볼 수 있습니다.

운영체제 작업 스케줄러나 배포 플랫폼의 예약 작업에는 다음 명령을 등록하면 됩니다.
이미 유효한 판정은 건너뛰고 신규·변경 공고만 다시 계산합니다.

```bash
python -m tools.refresh --collect
```

> **연습용 더미 데이터는 들어 있지 않습니다.** 화면에 뜨는 공고는 전부 기업마당·
> K-Startup 오픈API에서 받은 실제 공고이고, '원문 공고' 링크도 실제 페이지로 갑니다.
> 지어낸 공고가 섞이면 담당자가 어느 게 진짜인지 알 수 없고 링크도 죽기 때문입니다.

서버는 IPv4(`127.0.0.1`)와 IPv6(`::1`) **양쪽**에 붙습니다. 윈도우에서 `localhost`는
IPv6로 먼저 해석되는데 한쪽에만 붙여 두면 "서버는 떠 있는데 브라우저에서만 안 열리는"
상황이 생기기 때문입니다. 그래도 안 열리면 `http://127.0.0.1:8000` 을 써 보세요.

서버가 이미 떠 있으면 두 번째 실행은 **‘이미 사용 중’이라고 알리고 멈춥니다.** 파이썬 기본값(`allow_reuse_address=True`)은 윈도우에서 두 인스턴스가 같은 포트에 조용히 함께 붙게 만드는데, 그러면 요청이 옛 프로세스로도 가서 코드를 고치고 다시 켜도 반영이 안 된 것처럼 보입니다.

CLI로 전 과정을 한 번에 보려면:

```bash
python demo.py
```

성능을 숫자로 확인하려면:

```bash
python score.py
```

## 인증키 넣기

키가 **하나도 없어도** 캐시된 공고와 규칙 판정으로 전 기능이 동작합니다. 실제 공고를
받아오려면 아래 파일에 키를 붙여 넣으세요 (`.gitignore`로 제외되어 있습니다).

| 파일 | 키 | 발급처 |
|---|---|---|
| `clova_api_key.txt` | CLOVA Studio API Key | 네이버클라우드 CLOVA Studio |
| `clova_tuned_task.txt` | 튜닝 작업 ID *(선택)* | CLOVA Studio 학습 완료 후 발급 |
| `bizinfo_key.txt` | `crtfcKey` | [기업마당 지원사업정보 API](https://www.bizinfo.go.kr/apiDetail.do?id=bizinfoApi) |
| `datagokr_key.txt` | `serviceKey` (**Decoding 키**) | [공공데이터포털 15125364](https://www.data.go.kr/data/15125364/openapi.do) |

환경변수 `CLOVA_API_KEY` / `BIZINFO_KEY` / `DATA_GO_KR_KEY` 로도 넣을 수 있습니다.

> 공공데이터포털은 같은 키를 Encoding형·Decoding형 두 가지로 보여줍니다. 우리에게
> 필요한 건 Decoding 키인데, 화면에서 둘이 나란히 붙어 있어 Encoding 키를 넣기
> 쉽습니다(그러면 `%2B`가 `%252B`로 이중 인코딩돼서 키가 멀쩡한데도 403
> `SERVICE_KEY_IS_NOT_REGISTERED_ERROR`가 납니다). **어느 쪽을 넣어도 되도록
> `tools/keys.py`가 알아서 되돌립니다.**

키를 넣은 뒤:

```bash
python -m tools.ingest --dry-run   # 응답 원본 필드명 확인
python -m tools.ingest             # 실제 수집
```

### ⓪ 공고 첨부파일 — `tools/bizinfo_client.py`

기업마당은 첨부를 두 쌍으로 줍니다. **신청서 서식을 받으러 공고 사이트를 다시 찾아갈
필요가 없다**는 게 실무에서 큰 차이입니다.

| 필드 | 내용 | 실측 |
|---|---|---|
| `fileNm` / `flpthNm` | 신청서 **서식** (한글 양식 등) | 388/500건 |
| `printFileNm` / `printFlpthNm` | **공고문** 본문 파일 | 500/500건 |

한 공고에 파일이 여러 개면 이름도 경로도 `@`로 이어 붙여 한 문자열로 옵니다(388건 중
171건). 같은 자리끼리 짝지어야 이름과 링크가 어긋나지 않습니다.

링크는 GET에 `Content-Disposition: attachment` 로 파일을 그대로 내려주므로, 화면에서
누르면 바로 저장됩니다. (`HEAD` 요청은 403으로 막혀 있어 링크 검증에 쓸 수 없습니다 —
GET으로 확인해야 합니다.) 초안 탭에는 **서식 파일만** 따로 띄워, 만든 초안을 옮겨 담을
대상을 바로 옆에 둡니다. K-Startup은 첨부를 제공하지 않고 웹페이지 URL만 줍니다.

### ①-1 맞춤 추천 — `agent/recommend.py`

공고가 수백 건이면 마감순 목록만으로는 부족합니다. 담당자가 위에서부터 훑다 지치고,
정작 우리 회사에 맞는 공고는 아래 묻힙니다. 그래서 **회사 프로필에 맞는 공고를 목록
맨 위에 따로 올립니다.**

**LLM을 쓰지 않습니다.** 공고마다 부르면 700건에 수십 분이 걸리고 순위가 매번
흔들립니다. 지역·업종·지원분야·마감은 코드로 비교할 수 있어서, 자격 판정과 같은
분업을 따릅니다 — 731건 채점에 **0.02초**입니다.

| 신호 | 점수 |
|---|---|
| 우리 시·도 대상 / 전국 대상 | +30 / +12 |
| **다른 지역·시군구 전용** | 제외 |
| 제조업 대상 · 우리 업종 키워드(전자부품·ECU·SMT…) | +20 / 최대 +20 |
| **제조업체가 못 쓰는 업종**(음식점·미용업…) | 제외 |
| 지원 내용(공정·설비 > 기술개발 > 수출 > 자금 > 인력…) | +8~22 |
| 마감 D-3~30 / D-2 이하(준비 시간 촉박) | +14 / −8 |
| 이미 '가능'으로 판정됨 / '불가' | +40 / 제외 |

**왜 추천했는지 반드시 함께 보여줍니다.** 근거 없는 추천 목록은 담당자가 한 번 훑고
무시합니다. 점수 대신 사람이 읽는 이유를 답니다:

```
D-12  [전남광주] 첨단로봇ㆍAI 활용 중소기업 제조혁신 사업 기업지원(실증지원)   [가능]
      추천 이유: 신청 가능으로 판정됨 · 광주광역시 소재 기업 대상 · 제조업 대상 · 공정·설비 · D-12
```

추천은 **지금 걸린 필터 안에서** 고릅니다 — 화면에 없는 공고를 추천하면 눌렀을 때
목록에서 못 찾습니다.

> **여기서 잡은 버그.** 시·군·구 인식 정규식이 너무 헐거워 `청년친화도시`를 시·군·구로
> 읽고 광주 공고를 '다른 지역'이라며 제외했습니다. `연구`, `지구` 같은 말도 마찬가지였
> 습니다. 앞부분을 1~3글자로 좁히고 앞뒤 한글 경계를 걸어 고쳤습니다. **자격 판정도 같은
> 함수를 쓰므로, 잘못된 '불가'를 내던 문제가 함께 고쳐졌습니다.**

### ① 중복 통합 — `tools/dedupe.py`

같은 사업이 두 기관에 다른 제목으로 올라옵니다.

```
기업마당  : 2026년 광주광역시 중소기업 스마트공장 구축지원사업 모집공고(1차)
K-Startup : [광주] 중소기업 스마트공장 구축 지원 참여기업 모집
```

세 단계로 좁힙니다.

1. **정규화** — 괄호·연도·차수·상용어(`모집공고`, `참여기업`, `지원사업`…)를 걷어내고
   공백을 없애 '사업의 알맹이'만 남깁니다.
2. **블로킹** — 마감일 ±3일 이내이고 서로 다른 기관에서 온 쌍만 후보로 봅니다.
   같은 기관 안의 1차/2차 공고는 정상적으로 별개 사업이므로 비교하지 않습니다.
3. **유사도** — `difflib` + 토큰 자카드 + **containment**를 5.5:2:2.5로 섞습니다.
   containment 비중이 가장 큰 이유는 교차 게시된 공고가 보통 한쪽이 더 길기 때문입니다
   (짧은 쪽이 긴 쪽에 얼마나 들어 있나를 봅니다).
   **0.85 이상은 자동 통합**, **0.55 미만은 분리**, 그 사이 경계 구간만 하이퍼클로바X에
   "같은 사업인가?"를 물어봅니다.

경계 구간에만 LLM을 쓰는 이유: 전부 맡기면 느리고 비싸며, 무엇보다 매번 결과가 흔들려
재현이 안 됩니다. 확실한 건 코드가 정하고 애매한 것만 물어봅니다.

### ② 자격 판정 — `agent/eligibility.py`

**LLM에게 최종 판정을 맡기지 않습니다.**

```
1단계 (LLM)    공고문 → 구조화된 요건 {축, 연산자, 값, 공고문 원문 인용}
2단계 (파이썬)  요건 + 회사 프로필 → 요건별 가능/불가/확인필요
```

"업력 7년 미만"과 "설립일 2019-03-11"을 비교하는 건 뺄셈입니다. 뺄셈을 LLM에게 시키면
대체로 맞지만 가끔 틀리고, 같은 질문에 같은 답을 준다는 보장이 없습니다. 지원 자격은
틀리면 담당자가 헛수고를 하거나 기회를 놓치는 문제라 재현 가능한 쪽이 옳습니다. LLM은
자유 문장을 구조로 바꾸는 일만 맡고, **판단은 코드가 합니다.**

**근거 없는 요건은 버립니다.** LLM이 뽑은 요건에는 공고문 원문 인용이 반드시 붙어야
하고, 그 문장이 실제로 공고문에 있는지 코드가 대조합니다. 없으면 지어낸 것으로 보고
폐기합니다. 화면의 판정표에 인용이 항상 함께 뜨는 이유이기도 합니다 — 담당자가 5초 만에
'이 판정이 맞나'를 직접 확인할 수 있어야 합니다.

**종합 판정** — 불가가 하나라도 있으면 불가 → 없고 확인필요가 있으면 확인필요 →
전부 통과면 가능. 요건을 하나도 못 뽑았으면 '가능'이라 단정할 근거가 없으므로 확인필요.

**중복 통합의 실익이 여기서 회수됩니다.** 기업마당 공고에는 없는 '신청 제외대상'이
K-Startup 쪽에만 적혀 있는 일이 흔한데, 통합된 공고는 양쪽 원문을 함께 읽어 판정합니다.

**'확인필요'로 새는 걸 줄입니다.** 실데이터에서 확인필요가 지나치게 많았고, 원인은 두
가지였습니다.

- **시·군·구를 몰랐다** — `금천구`, `사천시` 같은 요건을 시·도 목록만으로는 판정하지 못해
  전부 확인필요로 샜습니다. 광주 광산구인 우리에게는 분명한 '불가'입니다. 다만 `남구`·
  `중구`처럼 여러 시·도에 같은 이름이 있는 자치구는 단정하지 않고 확인필요로 둡니다.
- **명백히 다른 업종을 몰랐다** — `일반ㆍ휴게음식점`, `이ㆍ미용업소` 대상 사업도
  확인필요였습니다. 제조업체가 신청할 수 없는 게 분명한 업종 목록(`_NON_MANUFACTURING`)에
  걸리면 '불가'로 확정합니다. 목록은 **일부러 좁게** 유지합니다 — `AI 분야`, `항공기업`
  처럼 걸칠 여지가 있는 표현까지 걸러 내면 신청할 수 있는 공고를 놓치기 때문입니다.

### ③ 신청서 초안 — `agent/drafter.py` · `agent/formspec.py` · `tools/formdoc.py`

**항목을 첨부된 신청서 서식에 맞춥니다.** 초안을 잘 써 줘도 항목이 서식과 다르면
담당자가 서식을 따로 열어 옮겨 적어야 합니다. 그 왕복을 없애는 게 목적입니다.

`tools/formdoc.py`가 서식 첨부를 내려받아 글자를 뽑습니다 — **표준 라이브러리만으로**:

| 형식 | 방법 |
|---|---|
| `.hwpx` `.docx` | ZIP + XML. `ElementTree`로 트리를 훑어 문단과 **표**를 구분합니다 |
| `.hwp` | OLE 복합문서를 직접 파싱(`_CFB`). 파이썬에 OLE 리더가 없고 pip 설치를 안 하기로 했으므로, 스트림 하나 꺼내는 데 필요한 만큼만 구현했습니다. 본문은 zlib 압축이라 풀어서 레코드(`HWPTAG_PARA_TEXT`)를 훑습니다 |
| `.zip` | 안을 풀어 한 단계만 재귀 |
| `.pdf` | **미지원** — 라이브러리 없이 신뢰할 만한 추출이 어렵습니다 |

**표를 행 단위로 살립니다.** 공고문에서 제출서류와 심사기준은 거의 항상 표에 들어
있는데, 글자만 긁으면 셀이 한 줄씩 흩어져 **행 관계가 사라집니다.**

```
잘못         구분 / 연번 / 제출서류 목록 / 부수      ← 머리행이 네 줄로 쪼개짐
             공통 / ① / 【서식 1】 사업 참여신청서 / 1부  ← 한 행이 네 줄로

올바름       구분 | 연번 | 제출서류 목록 | 부수
             공통 | ① | 【서식 1】 사업 참여신청서 | 1부
```

이게 무너지면 "어떤 서류가 몇 부인지", "이 항목이 어느 구분에 속하는지"를 읽는 쪽이
맞출 수 없습니다. hwpx/docx는 `<tbl>`→`<tr>`→`<tc>` 를 따라가고, hwp는 표 레코드와
셀 좌표를 읽어 같은 행을 잇습니다.

> **HWP 파싱에서 걸린 함정 둘.**
> ① 스펙이 제어문자를 'inline'(4~9,19,20)과 'extended'로 나누는데, 'inline'은 크기가
> 아니라 *본문 흐름 안에 놓인다*는 뜻이라 **둘 다 8워드(16바이트)를 차지합니다.**
> inline을 1워드로 처리했더니 뒤따르는 파라미터를 글자로 읽어 `…필수 첨부 浥%！ÿ`
> 같은 깨진 꼬리가 붙었습니다.
> ② 표(`HWPTAG_TABLE`)와 그 셀(`HWPTAG_LIST_HEADER`)이 **같은 level에 놓입니다**
> (실측: 둘 다 level 2). 표 종료 조건을 `level <= 표 레벨`로 뒀더니 첫 셀을 만나자마자
> 표가 닫혀 셀이 하나도 안 묶였습니다. `<` 여야 합니다. 셀 좌표(col, row)는
> LIST_HEADER의 offset 8·10에 있습니다.

**읽는 순서가 중요합니다.** 첨부 하나만 골라 거기서 전부 뽑으면 안 됩니다.

```
1단계  공고문을 먼저 읽는다        → 제출서류 목록을 얻는다
2단계  같은 공고문 뒤쪽을 계속 본다 → 서식이 붙어 있으면 작성 항목도 여기서 얻는다
3단계  항목을 못 얻었으면          → 다른 첨부(서식 파일)를 점수순으로 열어 본다
```

제출서류 목록은 거의 항상 공고문에 있고(오픈API 응답에는 없습니다), **신청서 서식이
공고문 파일 뒤에 그대로 붙어 있는 경우도 흔합니다.** 그래서 공고문을 먼저 읽어 서류와
항목을 같이 노립니다.

> 예전에는 공고문에서 제출서류를 찾으면 **거기서 멈춰** 서식 탐색을 중단했습니다.
> 그래서 신청서 양식이 따로 붙어 있어도 읽지 않았습니다. 지금은 항목을 얻을 때까지
> 계속 찾고, 제출서류는 읽은 파일마다 합칩니다.

파일명 점수(`신청서`·`사업계획`·`양식` +, `공고문`·`포스터`·`FAQ` −)로 3단계의 순서를
정합니다. 기업마당의 서식/공고문 구분이 자주 어긋나기 때문입니다(‘포스터.pdf’, ‘FAQ’가
서식으로 분류돼 있었습니다).

`agent/formspec.py`가 그 글자를 세 갈래로 정리합니다(LLM 구조화 + 규칙 폴백):

- **작성 항목** — 문단을 써야 하는 것. 초안의 항목이 됩니다
- **기입란** — 값만 채우는 칸(회사명·사업자등록번호…). 초안에 문단을 쓰지 않고 목록으로만 안내
- **제출서류** — 서식이 함께 내라고 요구하는 서류. ④ 점검에 합쳐집니다

> **공고문 목차를 작성 항목으로 착각하던 문제.** 첨부가 공고문일 때 그 목차
> (`사업개요`, `지원내용`, `추진일정`, `기타사항`…)를 신청자가 쓸 항목으로 내놓았습니다.
> 프롬프트에서 (가)서식과 (나)공고문을 구분하게 하고, 그래도 새어 나오면
> `_ANNOUNCEMENT_HEADINGS` 목록으로 **코드가 확정적으로 걷어냅니다.** 항목을 못 얻어도
> 제출서류는 건집니다 — 공고문에도 제출서류 목록은 흔히 있습니다.

**서식을 못 읽어도 담당자가 이어받을 수 있습니다.** 첨부가 없거나 PDF 서식이면 기본
구성(사업 개요·필요성·추진 계획·기대효과)으로 쓰고, 그 사실을 초안 알림에 밝힙니다.
담당자가 실제 양식을 확인했다면 **‘작성 항목 고치기’**에 항목을 한 줄씩 적어 그 항목으로
다시 쓰게 할 수 있습니다(`1.`, `■` 같은 번호·기호는 자동으로 떨어집니다). 도구가 못
읽었다고 담당자까지 기본 구성에 갇힐 이유가 없습니다.

실측: 신청서 서식이 붙은 공고 표본 15건 중 **11건**에서 실제 작성 항목을 뽑았습니다
(`기업현황`, `사업의 필요성`, `추진계획`, `기대효과` 등). 나머지 4건은 ‘착한가격업소 지정
신청서’처럼 서술 항목 없이 기입란만 있는 서식이라 항목이 없는 게 맞습니다.

과거 신청서(`data/past_applications/`)에서 항목별로 비슷한 문항을 찾아
(`tools/past_search.py`, TF-IDF 방식) 그 항목에 맞춰 초안을 씁니다.

**빈 서식은 재료에서 걸러냅니다.** 담당자가 올리는 파일에는 '작성이 끝난 신청서'와
'빈 서식'이 섞입니다. 빈 서식이 재료로 들어가면 분량만 못 채우는 게 아니라 서식에 딸린
예시 문장이 우리 회사 이야기인 양 초안에 옮겨 적힐 수 있습니다. 문항 제목이
`본문 (휴먼명조, 12pt)`·`사업계획서 작성지침 및 유의사항` 처럼 서식에만 나오는 꼴이거나
내용이 120자에 못 미치면 뺍니다 — 본문까지 뒤지는 것보다 제목만 보는 쪽이 오판이 적습니다.
(실제 업로드 파일 하나가 46문항 중 34개가 이런 경우였습니다.)

거른 결과는 **업로드할 때 담당자에게 알립니다.** 조용히 걸러 버리면, 파일을 올렸는데도
초안이 그대로인 이유를 알 길이 없습니다.

**항목을 하나씩 따로 생성합니다.** 한 번의 호출로 모든 항목을 받으면 응답 길이 한도를
항목 수로 나눠 쓰게 돼서 항목마다 두세 문장으로 쪼그라듭니다 — 사업계획서에 넣기엔
턱없이 짧습니다. 항목당 한 번씩 부르면 각 항목이 제 분량을 갖습니다.

| | 이전 (한 번에 전부) | 지금 (항목별 생성) |
|---|---|---|
| 항목당 분량 | 150~200자 | **800~900자** |
| 초안 전체 | 600~800자 | **2,300~3,600자** |
| 생성 시간 | 10~20초 | 30초~1분 |

분량은 참고 자료의 양에 비례합니다. `data/past_applications/` 에 실제 제출했던 신청서를
넣을수록 내용이 구체적이고 길어집니다.

#### 분량이 짧았던 진짜 이유 네 가지

항목별 생성으로 바꾼 뒤에도 실측하면 항목당 400자에서 끝났습니다. 원인을 하나씩
재 보니 넷이 겹쳐 있었고, 모두 프롬프트가 아니라 **코드 쪽 문제**였습니다.

**① 공고문 본문이 프롬프트에 안 들어갔습니다.** `notice_text`(첨부 공고문에서 뽑아낸
최대 6,000자)가 인자로 넘어오기만 하고 프롬프트에 한 번도 쓰이지 않았습니다. 모델이
제목·개요 몇 줄만 보고 쓰니 사업 내용을 알 수 없어 길게 쓸 수가 없었습니다.

**② 프롬프트가 스스로 분량을 깎고 있었습니다.** 일반론 padding을 막으려고 넣은
"재료가 바닥나면 거기서 멈춰라 / 묽은 열 줄보다 단단한 다섯 줄이 낫다"가 그대로
분량 상한이 됐습니다. 일반론 금지는 그대로 두되, **"멈춰라"를 "더 깊이 쪼개라"로**
바꿨습니다 — 새 사실을 지어내지 않고 분량을 늘리는 유일한 길입니다.

**③ 개조식이 2단이라 구조적으로 짧았습니다.** `O 대항목` / `- 하위항목` 두 단만
쓰게 했는데, 하위항목은 "한 줄로 끝내는 명사형"이라 대항목 3개 × 하위 3줄 = 400자에서
끝날 수밖에 없습니다. **3단(`· 세부 근거`)을 넣어** 주장마다 방법·순서·판단 기준을
붙이게 했습니다. 늘어난 분량이 전부 근거라 심사에서도 유리합니다.

> 여기에 후처리 버그가 하나 겹쳐 있었습니다. `_BULLET_RE`가 `·`를 `-`로 바꾸고 있어서,
> 모델이 3단으로 써 보내도 코드가 2단으로 납작하게 만들었습니다.

**④ 호출 한도(429)에 걸린 항목이 조용히 빠졌습니다.** 항목마다 따로 부르니 초안 한
건에 호출이 몰려, 4개 항목 중 2개만 생성되고 나머지는 429로 사라졌습니다. 담당자
눈에는 "초안이 짧다"로만 보입니다. `_post`에 **재시도(2·5·12초, `Retry-After` 존중)**를
넣고, 애초에 걸리지 않도록 항목 사이에 2.5초 간격을 뒀습니다 — 걸린 뒤 기다리는 것보다
처음부터 띄우는 편이 전체로는 빠릅니다.

그래도 짧게 나오는 항목이 있어 **하한을 코드로 만들었습니다**(`MIN_SECTION_CHARS = 700`).
그보다 짧으면 한 번 더 불러 이어 쓰게 하고, 늘린 결과가 원본보다 짧으면 버립니다 —
이어 쓰라고 했는데 요약해 오는 경우가 있어, 그때 덮어쓰면 초안이 더 나빠집니다.

실측(같은 공고, 첨부 서식 3항목): **403자 → 2,543자**, 항목당 808 / 890 / 845자.

**생성 후 다듬습니다.** 모델이 '본문만 쓰라'는 지시를 어기고 제목을 되풀이하거나
(`**과제 지원의 필요성**`) 마크다운 강조를 섞는 일이 잦아 코드가 걷어냅니다. 문체도
한 신청서 안에서 '~합니다'와 '~한다'가 섞이는데, 사람이 읽으면 바로 티가 나므로
문장 끝 어미를 문어체로 통일합니다(`_to_formal`).

**숫자는 AI가 만들지 않습니다.** 매출액·인원 수·설립연도가 필요한 자리에는
`{{매출액}}` 같은 자리표시자만 쓰게 하고, 생성 후 파이썬이 회사 프로필의 실제 값으로
바꿔 넣습니다. 프로필에 없는 값은 `[확인 필요: …]` 로 남깁니다 — 비어 있는 건 눈에
띄지만, 틀린 숫자는 안 띕니다.

모델이 `{{종업원 수}}`, `{{연매출}}` 처럼 제 나름의 이름을 지어 쓰는 일이 잦아
**별칭을 받아 줍니다**. 그러지 않으면 프로필에 값이 멀쩡히 있는데도 담당자가 손으로
채워야 합니다. (프롬프트에는 대표 이름만 안내합니다 — 별칭까지 나열하면 지시가
길어지고 모델이 오히려 헷갈립니다.)

**그래도 새는 수치는 표시합니다** (`flag_unverified_numbers`). 자리표시자를 쓰라고
못 박아도 모델은 "결함 검출 정확도 최소 95% 이상", "처리 속도 초당 10건" 같은 목표치를
스스로 만들어 냅니다. 그럴듯해서 담당자도 넘기기 쉬운데, 이 사업의 신청 유의사항은
허황된 수치를 탈락 사유로 명시하고 있습니다. 회사 프로필의 값과 **공고문 본문에 없는**
수치 뒤에 `[확인 필요]` 를 붙입니다.

> 지우지 않고 표시만 합니다. 목표 수치 자체는 사업계획서에 필요한 내용이라 통째로
> 없애면 글이 앙상해집니다. 담당자가 실제 목표로 바꿔 적으면 되는 자리입니다.
>
> 공고에 적힌 수치("총 사업비의 50% 이내")를 옮겨 쓴 것까지 의심하면 표시가 너무 흔해져
> 담당자가 전부 무시하게 되므로, 공고문 본문도 근거로 인정합니다. 도구가 제 손으로
> 채운 값(`{{매출액}}` → `18.5억원`)을 스스로 의심하던 오탐도 같은 이유로 고쳤습니다.

이 함수는 오래 **정의만 되고 아무 데서도 불리지 않는 죽은 코드**였습니다. 지어낸 숫자를
막는 장치가 사실상 꺼져 있었던 셈이라, `generate()` 에 연결했습니다.

### ③-1 말로 고치기 — `agent/editor.py`

초안을 받은 담당자가 실제로 하는 일은 '다시 쓰기'가 아니라 '여기만 손보기'입니다.
기대효과가 두루뭉술하다, 추진 계획에 일정이 없다, 문체가 딱딱하다 — 항목을 찾아
직접 고치는 대신 말로 하게 합니다.

```
담당자  기대효과가 두루뭉술해. 무엇이 얼마나 좋아지는지 넣어 줘
도구    ‘사업화지원 기대효과’ 항목을 고쳤습니다.
        확인이 필요한 값: 증가율, 신규 가맹점 수, 고용 창출 인원
```

**전체를 다시 만들지 않습니다.** 이 기능에서 가장 중요한 규칙입니다. '기대효과를 더
구체적으로'라는 요청에 초안 전체를 새로 쓰면, 담당자가 다른 항목에 직접 써 넣은 문장이
통째로 날아가고 되돌릴 방법도 없습니다. 그래서 두 단계로 나눕니다.

| 단계 | 하는 일 | 방식 |
|---|---|---|
| ① 라우팅 | 무엇을 고쳐 달라는 요청인지, **어느 항목**에 해당하는지 | Structured Outputs (`intent` / `targets` / `instruction` / `answer`) |
| ② 고쳐 쓰기 | 그 항목**만** 다시 쓴다 | 초안 생성과 같은 프롬프트 + '고치는 중' 지시 |

- 항목을 못 고르겠으면 **되묻습니다.** 엉뚱한 항목을 고치는 것보다 낫습니다.
- 문체·분량처럼 전체에 걸리는 요청은 `["*"]` 로 받아 모든 항목을 고칩니다. 모델이
  `*` 대신 '전체'·'모든 항목' 이라고 적어 보내는 일이 잦아 그것도 알아듣게 했습니다 —
  못 알아들으면 "전체적으로 문장을 짧게" 같은 흔한 요청이 통째로 실패합니다.
- 편집 요청이 아니라 질문(`"이 공고 마감이 언제야?"`)이면 본문을 건드리지 않고 답만
  합니다. 라우팅 프롬프트에 **공고 정보(마감일·D-day·지원대상·개요)를 함께 넘깁니다** —
  이게 없으면 도구가 답을 갖고 있으면서도 "확인할 수 없습니다"라고 답합니다.
- 보내는 것은 저장된 초안이 아니라 **화면에 보이는 글**입니다. 담당자가 방금 손으로
  고쳐 넣은 문장을 서버가 모른 채 덮어쓰면 안 됩니다.
- 한 번에 4개 항목까지만 고칩니다. 항목마다 따로 부르므로, 담당자를 1분 넘게
  기다리게 하느니 나머지는 다시 요청하게 하는 편이 낫습니다.

#### 대화가 할루시네이션 우회로가 되면 안 됩니다

초안 생성에 걸어 둔 안전장치를 **고친 글에도 똑같이 적용**합니다. 대화로 들어온
글이라고 느슨하게 두면, 담당자의 한 마디로 심사 지침이 탈락 사유로 못 박은 바로 그것을
도구가 대신 만들어 주게 됩니다.

실제로 시험한 결과입니다:

```
담당자  기대효과에 우리가 작년에 매출 30% 늘었고 ISO 9001 인증도 땄다고 써 줘
결과    본문에 '30%' 도 'ISO' 도 들어가지 않음
        인증 주장 → [확인 필요: 보유 인증 — 실제 내역을 적거나 이 줄을 지우세요]
```

#### 여기서 잡은 결함 두 가지

**지어낸 사람 이름.** '참여인력 현황' 항목에서 모델이 `연구원 김철수 | AI 딥러닝
전문가`, `연구원 이영희` 처럼 **없는 직원을 만들어 냈습니다.** 회사에 그런 사람이
없으면 허위 기재이고, 실존 인물이면 개인정보 문제입니다. 기존 `_CLAIM_GUARDS` 의
'인력 경력' 규칙은 `평균 경력 N년` 같은 표현을 보는데, 이름은 그런 낱말 없이 그냥
나오기 때문에 그대로 통과했습니다.

직책 낱말 곁의 사람 이름을 찾아, 프로필에 실제로 적힌 사람(대표자)이 아니면
`[확인 필요: 실명]` 으로 가립니다. **줄을 통째로 지우지 않고 이름만 가리는** 이유는
직책·역할처럼 쓸모 있는 내용까지 사라지면 담당자가 표를 처음부터 다시 짜야 하기
때문입니다.

> 한글은 사람 이름과 보통명사가 생김새로 구분되지 않아 오탐이 잘 납니다. 실제로
> `팀장 배치를`의 '배치'(성씨 배), `총괄하며 팀장`의 '하며'(성씨 하),
> `선임 연구원`의 '연구원'(성씨 연)이 모두 이름으로 잡혔습니다. 세 가지로 걸러냅니다 —
> **낱말이 시작하는 자리에서만** 찾고(`(?<![가-힣])`), **조사를 뗀 뒤** 견주고,
> **직책 낱말과 보통명사 목록**을 제외합니다. 시험 11건에서 오탐 0건입니다.

**표시가 두 번 붙는 문제.** `80%[확인 필요][확인 필요]` — 모델이 앞서 표시가 달린
본문을 그대로 옮겨 적은 뒤 코드가 또 붙였습니다. 이미 표시가 있으면 넘어갑니다.

### ③-2 초안 모델 튜닝 붙이기 (선택)

초안은 문체·구성이 중요해서 튜닝 효과가 큰 부분입니다. CLOVA Studio에서 학습시킨 모델을
**초안 생성에만** 연결할 수 있습니다(판정·중복 통합은 기본 모델 그대로).

> ⚠️ **튜닝 모델은 Structured Outputs를 지원하지 않습니다.** 공식 문서에 "이미지 입력,
> 추론, Function calling, Structured Outputs 미지원"이라고 명시돼 있습니다. 기본 초안
> 경로는 JSON 스키마로 형식을 강제하는데 튜닝 모델에는 그걸 쓸 수 없어서, **평문을 받아
> 파싱하는 경로**를 따로 두었습니다(`agent/drafter.py`의 `_TUNED_SYSTEM`,
> `parse_sections()`). 구분자는 `■`로 잡았습니다 — 신청서 본문에 거의 안 나오는 글자라
> 본문과 헷갈리지 않고, 학습 데이터도 같은 형식이라 모델이 이 형식을 그대로 익힙니다.

**1. 학습 데이터 만들기**

```bash
python -m tools.export_training      # data/training_draft.csv
```

과거 신청서(`data/past_applications/*.md`)를 CLOVA Studio 학습용 CSV로 바꿉니다.
컬럼은 규격대로 `System_Prompt, C_ID, T_ID, Text, Completion` 순서이고, C_ID는 0부터
1씩 증가합니다(단발성 학습이라 T_ID는 전부 0).

입력(`Text`)을 **서비스가 실제로 만드는 프롬프트와 같은 형식**으로 맞추는 게 핵심입니다.
형식이 어긋나면 학습해도 서비스에서 효과가 안 납니다. 정답(`Completion`)은 실제 제출했던
문장을 `■ 항목명` 형식으로 담습니다.

> 표본 수가 중요합니다. 지금 들어 있는 연습용 과거 신청서로는 10건밖에 안 나옵니다.
> 실제로 제출했던 신청서를 `data/past_applications/` 에 `## 문항제목` 으로 나눠 넣고
> 다시 실행하세요.

**2. CLOVA Studio에서 학습**

CSV를 Object Storage에 올린 뒤 콘솔의 **학습** 메뉴(플레이그라운드는 프롬프트 실험용이라
튜닝은 여기서 합니다)에서 학습을 만듭니다. 베이스 모델·에폭 등은 콘솔에서 고릅니다.

**3. 연결**

학습이 끝나면 나온 **작업 ID**를 `clova_tuned_task.txt` 에 붙여 넣으면 끝입니다
(환경변수 `CLOVA_TUNED_TASK_ID` 도 됩니다). 호출 경로가 기본 모델과 다릅니다:

```
기본   POST /v3/chat-completions/{모델명}
튜닝   POST /v3/tasks/{taskId}/chat-completions
```

튜닝 모델 호출이 실패하면(학습 미완료, 작업 삭제 등) **자동으로 기본 모델로 내려가고**
그 사실을 초안 알림에 적습니다 — 튜닝 하나 때문에 초안 기능이 통째로 죽으면 안 되니까요.

**숫자 보호는 그대로입니다.** 튜닝 모델을 쓰든 안 쓰든 매출·인원은 자리표시자로만 쓰게
하고 코드가 프로필 값으로 치환하므로, 학습 데이터의 숫자가 새어 나오지 않습니다.

### ④ 점검 — `agent/checker.py`

문제 정의가 지목한 리스크를 그대로 겨냥합니다. 전부 **규칙 기반**입니다(빠르고 재현 가능).
**점검을 두 곳으로 나눴습니다** — 일이 일어나는 시점이 다르기 때문입니다.

#### 서류 준비 → 자격 판정 탭의 **체크리스트**

공고를 검토하는 단계에서 "무엇을 떼러 가야 하나"를 봅니다. 발급에 며칠 걸리는 서류가
있어 **초안을 쓰기 전에** 알아야 합니다.

경고 목록이 아니라 체크리스트인 이유: **서류를 실제로 준비했는지는 사람만 압니다.**
도구가 "없습니다"라고 단정하면 이미 떼어 둔 서류에도 빨간 경고가 뜨고, 그런 게 몇 개
쌓이면 담당자가 경고 전체를 무시하게 됩니다. 체크 상태는 `doc_checks` 테이블에 남습니다.

> **보유 서류는 회사 프로필에 두지 않습니다.** 납세증명서처럼 유효기간이 있는 서류가
> 대부분이라 '보유 중'이라는 정보가 며칠이면 틀린 값이 되고, 담당자가 프로필과
> 체크리스트 두 곳을 관리하게 됩니다. 공고마다 체크하는 편이 실제와 맞습니다.

준비 방법이 다르므로 두 갈래로 나눕니다. 처음에는 모두 비어 있습니다.

| 구분 | 뜻 |
|---|---|
| **발급** | 떼러 가야 하는 서류 — 며칠 걸리는 것이 있음 |
| **작성** | 이번에 써야 하는 서류(신청서·사업계획서) — 초안 탭이 도움 |

서류 목록은 첨부(공고문·서식)에서 뽑고, 어느 파일에서 왔는지 함께 밝힙니다. 마감 임박·
마감 지남 경고도 여기 붙습니다.

#### 글 점검 → 초안 탭의 **오탈자 · 수치 불일치**

초안을 다 쓴 **뒤에** 볼 일입니다. 글이 없으면 검사할 것도 없습니다.

- **수치 불일치** — 본문의 상시근로자·매출액·설립연도를 프로필과 대조합니다.
  *제공 기업이 지목한 '문서 간 수치 불일치' 리스크를 직접 겨냥합니다.*
- **표기 오류** — 회사명 표기 흔들림, 중복 공백, 반복 문장부호, 닫히지 않은 괄호.

초안 화면에 "사업자등록증을 떼세요" 같은 말이 섞이면, 정작 봐야 할 "본문의 인원 수가
프로필과 다릅니다" 같은 경고가 묻힙니다.

## 성능

`python score.py` 로 잽니다. 두 가지를 봅니다.

| | 재는 것 | 왜 |
|---|---|---|
| **① 중복 제거** | precision · recall | precision이 낮으면 서로 다른 공고를 합쳐 **지원 기회를 통째로 날린** 것이고, recall이 낮으면 같은 공고를 두 번 검토하게 만든 것입니다. 전자가 훨씬 나쁩니다 |
| **② 자격 판정** | 정확도 · **위양성** | 위양성(불가·확인필요를 '가능'이라 답한 건수)은 담당자가 쓸 수 없는 공고에 서류를 준비하게 만드는 가장 비싼 실수라 따로 뽑습니다 |

> **지금은 정답셋이 비어 있습니다.** 연습용 더미 공고를 걷어내면서 그것과 짝을 이루던
> 정답셋(`data/golden_dupe.csv`, `data/golden_eligibility.csv`)도 함께 없앴습니다.
> 지어낸 공고로 잰 점수는 실제 성능을 말해 주지 않기 때문입니다.
>
> **정답셋 만드는 법** — 수집된 실제 공고 중 30~50건을 골라
> `data/golden_notices.json` 으로 저장하고(형식은 `notices_cache.json` 과 같습니다),
> 사람이 직접 라벨을 붙입니다.
>
> | 파일 | 컬럼 | 내용 |
> |---|---|---|
> | `golden_dupe.csv` | `notice_a, notice_b, same` | 공고쌍이 같은 사업인가 (1/0) |
> | `golden_eligibility.csv` | `notice_id, verdict, note` | 가능 / 불가 / 확인필요와 그 이유 |
>
> 이 정답셋의 역할은 "완벽함의 증명"이 아니라 **회귀 방지**입니다. 실제로 개발 중
> 여러 판정 버그가 이 채점에서 드러났습니다 — "총 사업비의 50% 이내"라는 지원 조건의
> 숫자를 인원 요건으로 잘못 읽어 판정이 뒤집히던 문제, "체납 중인 기업은 제외"를
> 이중 부정으로 처리해 결과가 반대로 나오던 문제 등입니다.

**측정해 둔 성질 하나** — 자격 판정 정확도는 실행마다 조금씩 흔들립니다(요건 추출이
LLM이라서). 다만 **위양성은 모든 실행에서 0건**이었습니다. 흔들리더라도 '가능'을
남발하는 쪽으로는 흔들리지 않습니다. 판정 자체를 코드가 하고 LLM은 문장을 구조로
바꾸기만 하는 설계가 이 성질을 만듭니다.

## 오프라인에서도 동작합니다

본선 현장에서 네트워크나 인증키에 문제가 생겨도 데모가 멈추지 않게 설계했습니다.

| 상황 | 동작 |
|---|---|
| 한 기관 API 실패 | 다른 기관 것만으로 계속 진행 |
| 두 기관 모두 실패 | `data/notices_cache.json`(마지막 성공분)으로 폴백 |
| 하이퍼클로바X 없음 | 정규식 규칙으로 요건 추출, 중복은 점수만으로 판정 |
| LLM 호출 실패 | 초안은 뼈대 문장으로 대체, 점검은 원래 규칙 기반이라 영향 없음 |

키 파일을 전부 비우고 `python demo.py` 를 실행하면 이 경로를 확인할 수 있습니다.

```
   ├─ golden_notices.json   채점용 공고 묶음 (정답셋과 짝) — 지금은 비어 있음
   ├─ notices_cache.json    마지막 실수집 결과 (오프라인 폴백용)
   ├─ golden_dupe.csv       중복 정답셋 · golden_eligibility.csv  판정 정답셋
   ├─ company_profile.json  회사 프로필 · past_applications/  과거 신청서
   ├─ forms/                내려받은 첨부 서식 캐시 (자동 생성)
   └─ app.db                SQLite
```

> `golden_notices.json`과 `notices_cache.json`을 분리한 이유: 한 파일을 쓰면 실제 공고를
> 한 번 수집하는 순간 더미가 사라져 `score.py`가 채점할 대상을 잃습니다. 회귀 방지
> 장치를 실수로 없애지 않으려고 갈라 두었습니다.

## 화면

| 탭 | 하는 일 |
|---|---|
| **① 공고함** | 맨 위에 **우리 회사에 맞는 공고 5건**을 추천 이유와 함께 띄우고, 그 아래 마감 D-day 순 전체 목록. 중복 통합된 공고는 **사업 단위로 한 장만** 뜨고 `기업마당 · K-Startup 통합` 배지가 붙습니다. 상단에 `가능 N · 확인필요 N · 불가 N` 집계가 뜨고, **‘목록 전체 판정’**으로 지금 필터에 걸린 공고를 한꺼번에 판정합니다(진행 상황이 보이고 언제든 중지 가능). 지역·마감·판정으로 거를 수 있습니다. |
| **② 자격 판정** | 맨 위에 **사업 개요**(지원분야·개요·지원내용·지원대상·신청방법)를 두어 ‘이 사업이 뭘 해 주는가’를 이 화면에서 알 수 있게 했습니다. 그 아래 요건별 표 — 요건 / 우리 회사 값 / 판정 / **공고문 원문 인용**. 제출서류·신청 일정과 **공고 첨부파일**(서식·공고문)도 함께. |
| **③ 초안 · 점검** | **첨부 서식에서 읽어낸 항목 그대로** 초안을 만듭니다. 우측 **‘말로 고치기’**에 “기대효과에 숫자 목표를 넣어 줘” 처럼 적으면 **그 항목만** 다시 씁니다(바뀐 항목은 테두리로 표시). 상단에 서식 파일 링크와 '값만 채우면 되는 칸' 목록을 띄워, 서식을 열었을 때 뭘 채워야 하는지 미리 보여줍니다. 화면에서 고친 내용 그대로 점검하고, 전체 복사도 됩니다. |
| **회사 프로필** | 판정의 기준값. 저장하면 이전 판정 캐시가 자동으로 무효가 되어 다시 계산됩니다. 정해진 칸 외에 **회사마다 다른 항목(주생산품·설비 등)은 이름부터 직접 적는** 자유 항목으로 넣습니다. |

> **화면에 없는 프로필 값은 없는 것과 같습니다.** `extra`(주생산품·설비)와
> `prior_support`(최근 3년 수혜 이력)는 데이터에도 있고 초안·판정에도 쓰이는데,
> 정작 **입력 화면에 렌더링되지 않아** JSON을 손으로 고쳐야만 바꿀 수 있었습니다.
> `prior_support` 는 `"list"` 렌더링 코드까지 이미 있었는데 필드 목록에서 빠져 있었습니다.
> 담당자에게는 "그런 값이 아예 없는 도구"로 보입니다 — 화면에 내놓지 않을 값이면
> 애초에 판정·초안에 쓰지 말아야 합니다.
>
> `extra` 는 회사마다 적을 항목이 달라 칸을 미리 정해 둘 수 없으므로 **이름 / 내용 쌍**을
> 담당자가 직접 추가·삭제합니다. 이름이 빈 행은 저장할 때 버립니다.

**출처를 분명히 밝힙니다.** 판정 화면에 `자료 출처: 기업마당 + K-Startup 오픈API` 를
적고, **기관별 원문 공고 링크**를 따로 겁니다(통합된 공고는 양쪽 다). 담당자가 "이 판정이
어느 공고를 보고 나온 건가"를 원문에서 직접 확인할 수 있어야 도구를 믿습니다.

**API 키는 브라우저로 절대 내려보내지 않습니다.** 오픈API·하이퍼클로바X 호출은 전부
서버가 대신하고, 키는 서버 쪽 파일(또는 환경변수)에만 존재합니다.

## 과제 규칙 준수

- 공고 수집은 **공식 오픈API로만** 합니다. 기관 누리집 직접 크롤링 코드는 없습니다.
- **지어낸 공고는 하나도 없습니다.** 화면의 모든 공고는 두 기관 오픈API에서 받은 실제
  공고이고, 원문 링크도 실제 페이지로 갑니다. 문제 정의가 더미데이터를 허용하지만,
  실제 공고와 섞이면 담당자가 어느 게 진짜인지 알 수 없어 걷어냈습니다.
- 남은 것은 **회사 프로필**(`data/company_profile.json`) 하나뿐입니다. 문제 Pool이
  제시한 제공 기업(전자부품 제조업 / 10인 미만 / 광주)을 따른 값이며, 실제 회사 정보로
  바꿔 쓰면 됩니다.
